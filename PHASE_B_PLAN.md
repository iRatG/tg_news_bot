## Мотивация (корень проблемы)

Fact-checker — **топ-потребитель токенов**: 221k/мес (128k in + 93k out), 386 вызовов.
Он отклоняет **61% кандидатов**, и **76% отказов (181 из 237) = «дубликат темы»**.

Ключевое наблюдение из кода: сигнал `is_duplicate_topic` приходит от Perplexity
внутри самого дорогого вызова (`search_context_size="high"`,
`search_recency_filter="week"` — см. `agents/fact_checker.py:84,139`), и в промпте
**НЕТ истории наших публикаций**. Модель фактически судит «широко ли растиражирована
новость» по своему веб-поиску, а не «постили ли мы это».

При этом наши источники OpenAI/Anthropic/Google/DeepSeek — это **Google Alerts**,
то есть ленты синдицированных перепечаток. Одна новость приходит в 5 обёртках →
почти каждая триггерит «дубликат» → отсюда 76%.

**Вывод:** мы платим за самый дорогой вызов Perplexity, чтобы он раз за разом
отклонял то, что можно отсечь бесплатно и детерминированно ещё в researcher —
по совпадению с уже опубликованным. Плюс сигнал, возможно, режет реально новые
для канала истории только потому, что они синдицированы.

## Задачи

### B0 — Сначала измерить (данные, ~полдня) ⚠️ делать первым
Урок ретроспективы: «SOURCE_CAP добавили, не проверили на данных → потеряли время».
- Выборка отклонённых как «дубликат»: сколько реальных повторов уже опубликованного
  (по заголовку/URL) vs новых для канала историй, зарубленных зря.
- Распределение похожести заголовков кандидатов против `published_posts` за 7/30 дней —
  **откалибровать порог** дедупа на реальных данных.
- **Выход:** число ожидаемой экономии + выбранный порог + решение по B3.
- **Не меняет прод.**

### B1 — Детерминированный детектор near-duplicate (ядро, ~день)
Переписать `core/dedup.py`: near-duplicate по нормализованному `заголовок + content`
через shingle/MinHash или trigram-Jaccard. **Без API, без тяжёлых зависимостей**
(sentence-transformers НЕ тянем — 1GB VPS).
- **Улучшение:** дешёвый стабильный тестируемый сигнал взамен мёртвого
  `deepseek-chat` embeddings (всегда 404).
- **Критерий приёмки:** unit-тесты на парах «дубль / не дубль»; порог из B0.

### B2 — Дедуп ДО fact-checker в researcher (~полдня)
Встроить B1 в `researcher.fetch_and_rank()`: отбрасывать кандидатов, чей топик
совпадает с опубликованным за N дней, **до** передачи в fact-checker.
- **Улучшение:** −~40% вызовов fact-checker → экономия Perplexity; быстрее прогоны;
  меньше прогонов с «0 опубликовано» из-за перепечаток.
- **Файлы:** `agents/researcher.py`.

### B3 — Пересобрать роль fact-checker (~полдня, зависит от B0)
Дедуп теперь честно в researcher против нашей истории → арбитражный
`is_duplicate_topic` (без контекста наших постов) лишний и переусердствует.
- Убрать `is_duplicate_topic` из **жёстких** отказов (`agents/fact_checker.py:239`);
  оставить только проверку правды (`verified` + `confidence`).
- **Улучшение:** возвращаем реально новый контент, который режется зря;
  fact-checker делает одну работу.
- **Защита:** решение по данным B0. Если сигнал ловит настоящие повторы хорошо —
  оставить «мягким» (лог, не отказ) и понаблюдать.

### B4 — Убрать мёртвый код дедупа (~полчаса)
`dedup.py` (embeddings) не работал никогда: `EMBEDDING_MODEL="deepseek-chat"` → 404
→ `article_embeddings` пуста, `check_similarity` всегда 0.0, `save_embedding` всегда
падает. Analyst дёргает обе на каждый пост впустую.
- Заменить вызовы в `agents/analyst.py:170-209` на детектор B1; удалить мёртвый
  модуль и мёртвые настройки (`dedup_threshold`, `dedup_lookback_days`).
- **Улучшение:** −~195 строк мёртвого кода, минус безнадёжные API-попытки на пост.

### B5 — Гигиена БД (~полчаса)
- researcher грузит **все** URL в память каждый прогон (`agents/researcher.py:405`) —
  15k строк и растёт. Избыточно: вставка уже через `INSERT OR IGNORE` по уникальному
  `url`. Убрать полный скан таблицы.
- 13.9k NEW-статьи копятся вечно (пул смотрит только 7 дней). Добавить ежедневную
  чистку старых NEW (как снапшот подписчиков в 00:05).
- **Улучшение:** ограниченный рост БД, дедуп без O(n)-скана на прогон.

## Порядок и протокол проверки

Порядок: **B0 → B1 → B2 → (B3 по данным B0) → B4 → B5**.

Каждый шаг с изменением логики:
1. Проверить на реальных данных БД (не только логику кода) — урок ретроспективы.
2. Прогнать в тестовый канал **@manitrus** через dev-routing:
   ```
   docker exec -e ENVIRONMENT=development -e TELEGRAM_CHANNEL_TEST_ID=@manitrus \
     tg_news_bot python scripts/run_once.py [--digest|--arxiv]
   ```
3. Сравнить метрики до/после (вызовы fact-checker, published-rate).
4. Деплой по `RULES.md` (docker cp + restart), затем прод-мониторинг логов.

**Главный риск:** слишком агрессивный дедуп → пустые прогоны.
**Защита:** калибровка порога по B0 + тест на @manitrus перед продом.
